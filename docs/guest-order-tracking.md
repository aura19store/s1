# Guest order tracking rollout

This is a plan, not evidence that any production step has been performed. Stop at any failed or unproven checkpoint and keep transition protection in place. Neither a successful build nor a deployment status alone proves that all traffic has reached the intended version.

- New guest orders receive a random 256-bit tracking secret; only its SHA-256 digest is stored. It is returned once in the checkout response to the purchasing browser, over HTTPS, never in a tracking URL or in order-list/detail APIs. The customer must save it privately to use another device.
- Browser access uses a separate random HttpOnly host-only cookie and a server-side association for each order. Losing browser data does not delete an order; the saved secret is needed to regain access.
- Existing orders are not modified or automatically linked: the historical schema has no trustworthy guest-browser association or tracking secret. Self-service recovery for them is disabled until a reliable ownership-verification process is available. Admin access is unchanged. Support must not disclose order details based on order number, phone, name, or other public information alone.

## Protected transition sequence

1. **PRE-FLIGHT:** Review the actual production schema, migration prerequisites, migration runner and runtime roles, existing RLS policies and effective grants, including PUBLIC and inherited/default privileges, and external integrations. Inventory all production and alternative routes, versions and preview URLs, and in-flight requests. Prepare and review an exact backup of the existing policies, grants and RLS settings, and a rollback runbook. Test equivalent roles and migrations on a disposable clone. Do not infer the runtime role from the origin username or migration runner.
2. **Protect the transition first:** Establish and verify protection that prevents access to the old order-detail and confirmation paths and covers all relevant production and alternate routes, versions and in-flight requests. If complete coverage cannot be demonstrated, stop. Do not assume a single route, a preview toggle or a fixed wait proves coverage.
3. **Deploy the new protected tracking code** while transition protection remains in effect. The new checkout requires the tables created by `0005`; before `0005` succeeds checkout can fail. Do not open access or fall back to the old unprotected code during this interval.
4. **Keep protection in place during propagation and verification.** Deployment status or sampling one location does not prove global propagation or completion of in-flight requests. Stop if the protected new version's coverage cannot be established.
5. **Prove the actual Worker connection through Hyperdrive and the PostgreSQL session identity** (`current_user` and `session_user`) using an approved, trustworthy method. Verify effective privileges and RLS behavior of that runtime role; do not infer them from Hyperdrive's configured origin username. If this cannot be established under the approved constraints, stop. Check permissions on the new tables after `0005` creates them.
6. **Apply `0005_guest_order_tracking.sql` only after its prerequisites have been verified**, including the schema, runner, effective grants and behavior on an equivalent disposable clone. Verify creation, constraints, indexes, RLS, policies, effective browser-role privileges and runtime access. Keep protection active on failure.
7. **Apply `0006_private_order_data.sql` as a separate step**, only after the new protective code has been deployed and transition coverage verified, `0005` has succeeded, and the effect on existing `orders`, `order_items`, `customers`, their sequences, other roles and integrations has been reviewed. Confirm the actual runtime role retains the required access with RLS enabled. Never apply `0006` before deploying the new protective code.
8. **Verify isolation and effective permissions:** Check RLS, policies, table/column/sequence privileges and runtime-role access. Verify authorized and unauthorized order access, correct and incorrect tracking codes, legacy denial, checkout, status and deletion without creating real customer orders. Check integrations and historical data remain intact; stop on any mismatch.
9. **Open final access only after every checkpoint succeeds.** In particular, never open checkout before `0005` has been applied and verified; keep transition protection active until the protected version and all security and integration checks are confirmed.
10. **Rollback only according to the reviewed runbook.** Maintain protection while resolving failures; do not blindly restore old code that exposes orders, disable RLS, grant public access or change historical orders. Restoration of `0006` access-control metadata requires the reviewed exact backup of prior policies, grants and RLS settings.
